# Techy Tracker — પર્સનલ અને શેર્ડ એક્સપેન્સ ટ્રેકર (ગુજરાતી ગાઈડ)

નમસ્તે! **Techy Tracker** ના આ ડોક્યુમેન્ટેશનમાં તમારું સ્વાગત છે. આ ફાઈલ ખાસ એવી રીતે લખવામાં આવી છે કે જો તમને **Backend (બેકએન્ડ)** કે **Database (ડેટાબેઝ)** વિશે કંઈ જ ખબર ન હોય (તમે સાવ નવા/Beginner હોવ), તો પણ તમને આખો પ્રોજેક્ટ પાણીની જેમ સરળતાથી સમજાઈ જશે.

---

## 1. પ્રોજેક્ટનો ઓવરવ્યુ (Project Overview)

### આ પ્રોજેક્ટ શું છે?
**Techy Tracker** એ એક આધુનિક વેબ એપ્લિકેશન ( હિસાબ-કિતાબ રાખવાની એપ ) છે, જેમાં તમે તમારા **પોતાના (Personal)** અને **મિત્રો કે પરિવાર સાથે કરેલા ભાગિયા ખર્ચા (Shared/Split Expenses)** નો સંપૂર્ણ હિસાબ **ભારતીય રૂપિયા (₹ / INR)** માં રાખી શકો છો.

### આ પ્રોજેક્ટનો મુખ્ય હેતુ શું છે?
રોજબરોજના જીવનમાં જ્યારે આપણે મિત્રો કે રુમમેટ્સ સાથે જમવા જઈએ, ટ્રાવેલ કરીએ કે ઘરનું કરિયાણું લાવીએ, ત્યારે કોઈ એક વ્યક્તિ બિલ ચૂકવે છે (દા.ત. રૂષાંગી ₹500 ચૂકવે છે) અને બાકીના મિત્રોએ પોતાના ભાગના પૈસા તેને આપવાના હોય છે. 
આ એપનો હેતુ નીચે મુજબની સમસ્યાઓ હલ કરવાનો છે:
1. **તમારો પોતાનો સાચો ખર્ચ જાણવો:** ડેશબોર્ડ પર **"Total Expenses"** માં ગ્રુપના આખા બિલને બદલે **ફક્ત તમારા પોતાના ભાગનો જ ખર્ચ** ગણાય છે, જેથી તમને ખબર પડે કે મહિનામાં કે અઠવાડિયામાં તમારા ખિસ્સામાંથી ખરેખર કેટલો ખર્ચ થયો.
2. **કોણે કોને કેટલા રૂપિયા આપવાના છે (Pending vs Settled):** જ્યારે કોઈ ખર્ચ **Pending** હોય, ત્યારે દરેક સભ્યના નામની નીચે સ્પષ્ટ દેખાય છે કે *"Needs to pay ₹100.00 to rushangi"* (એટલે કે આ વ્યક્તિએ રૂષાંગીને ₹100 આપવાના બાકી છે). જ્યારે ખર્ચ **Completed** કરવામાં આવે, ત્યારે બધાનો હિસાબ **Settled** થઈ જાય છે.
3. **દરેક ફેરફારનો રેકોર્ડ (Logs):** જો કોઈ ખર્ચની રકમ કે સ્ટેટસ બદલે, તો નીચે **Logs** વિભાગમાં સમય સાથે નોંધ રહે છે કે કોણે શું ફેરફાર કર્યો.
4. **ડાર્ક મોડ અને મોબાઈલ ફ્રેન્ડલી UI:** મોબાઈલ અને કોમ્પ્યુટર બંનેમાં સરળતાથી વાપરી શકાય તેવું **React + Tailwind CSS** નું આકર્ષક ડિઝાઇન અને હેડરમાં એક ક્લિકથી ચાલતું **Dark / Light Mode** બટન.

## 2. પ્રોજેક્ટનો સંપૂર્ણ ફ્લો (Complete Application Flow)

ચાલો એક **વાસ્તવિક જીવનના ઉદાહરણ ( હોટલનું ઉદાહરણ )** દ્વારા સમજીએ કે આ એપ કેવી રીતે કામ કરે છે:
- **Frontend (React.js):** હોટલનું **મેનુ કાર્ડ અને ટેબલ** (જે યુઝરને સ્ક્રીન પર દેખાય છે).
- **Backend API (Python Flask):** હોટલનો **વેઈટર** (જે તમારો ઓર્ડર રસોડા સુધી લઈ જાય છે અને તૈયાર થયેલું જમવાનું પાછું લાવે છે).
- **Database (PostgreSQL + Prisma):** હોટલનું **રસોડું અને સ્ટોર-રૂમ** (જ્યાં બધો સામાન/ડેટા કાયમી સાચવવામાં આવે છે).

### સ્ટેપ-બાય-સ્ટેપ પ્રક્રિયા (Frontend ➔ Backend ➔ Database ➔ Frontend):

1. **સ્ટેપ 1 — યુઝર સ્ક્રીન પર બટન દબાવે છે (Frontend):**
   - ધારો કે તમે એપ ખોલી, **Expenses** ટેબમાં ગયા અને **"Record Expense"** બટન દબાવ્યું.
   - તમે ફોર્મમાં વિગત ભરી: *Title: "પીઝા પાર્ટી"*, *Amount: ₹1000*, *Paid By: Rutvik*, અને *Split With: 4 મિત્રો*. પછી તમે **"Record Expense"** (Save) બટન દબાવ્યું.

2. **સ્ટેપ 2 — ફ્રન્ટએન્ડ ડેટા ચેક કરે છે અને બેકએન્ડને મોકલે છે (Frontend ➔ Backend):**
   - સૌથી પહેલાં ફ્રન્ટએન્ડ ચેક કરશે કે કોઈ ખાનું ખાલી તો નથી ને? જો ખાલી હશે તો લાલ રંગમાં સરસ મેસેજ બતાવશે.
   - બધું બરાબર હશે તો ફ્રન્ટએન્ડ આ ડેટાનું એક પેકેટ (જેને ટેકનિકલ ભાષામાં **JSON** કહેવાય) બનાવશે અને વેઈટર એટલે કે **Backend API (`POST /api/expenses`)** ને મોકલશે.

3. **સ્ટેપ 3 — બેકએન્ડ હિસાબની ગણતરી કરે છે (Backend Processing):**
   - બેકએન્ડ (Python Flask) ચેક કરશે કે આ યુઝર લોગ-ઈન થયેલો છે કે નહીં (JWT Token દ્વારા).
   - ત્યારબાદ બેકએન્ડ ગણતરી કરશે: કુલ ₹1000 છે અને 4 સભ્યો છે, એટલે દરેકના ભાગમાં **₹250** આવશે.
   - જેણે પૈસા ચૂકવ્યા છે (Rutvik), તેનું સ્ટેટસ `isSettled = True` રાખશે, અને બાકીના 3 મિત્રોનું સ્ટેટસ `isSettled = False` (બાકી) રાખશે.

4. **સ્ટેપ 4 — ડેટાબેઝમાં ડેટા સેવ થાય છે (Backend ➔ Database):**
   - બેકએન્ડ **Prisma ORM** ની મદદથી **Database** ની અંદર 3 જગ્યાએ એન્ટ્રી પાડશે:
     1. `Expense` ટેબલમાં મુખ્ય ખર્ચ (₹1000) સેવ કરશે.
     2. `ExpenseParticipant` ટેબલમાં ચારેય મિત્રોના ₹250-₹250 ના ભાગ સેવ કરશે.
     3. `ExpenseAuditLog` ટેબલમાં પહેલો Log બનાવશે કે *"Rutvik એ ₹1000 નો ખર્ચ ઉમેર્યો"*.

5. **સ્ટેપ 5 — પાછો જવાબ સ્ક્રીન પર દેખાય છે (Database ➔ Backend ➔ Frontend):**
   - ડેટાબેઝ કહેશે: *"ડેટા સફળતાપૂર્વક સેવ થઈ ગયો!"*
   - બેકએન્ડ આ નવો સેવ થયેલો ખર્ચ ફ્રન્ટએન્ડ (React) ને પાછો આપશે.
   - ફ્રન્ટએન્ડ તરત જ સ્ક્રીન પર લીલા રંગનો મેસેજ (**Toast Notification**) બતાવશે અને તમારા લિસ્ટ તથા ડેશબોર્ડમાં નવો ખર્ચ અપડેટ કરી દેશે!

## 3. બેકએન્ડ કેવી રીતે કામ કરે છે? (How the Backend Works)

બેકએન્ડ ફોલ્ડર (`/backend`) ની અંદર અલગ-અલગ ફાઈલો રાખવામાં આવી છે જેથી કોડ ભેગો ન થઈ જાય. ચાલો દરેક ફાઈલનું કામ સાદી ભાષામાં સમજીએ:

1. **`backend/app.py` (મેઈન સર્વર ફાઈલ / મેનેજર):**
   - આ બેકએન્ડનું મુખ્ય દ્વાર (Entry Point) છે.
   - જ્યારે તમે સર્વર ચાલુ કરો ત્યારે આ ફાઈલ રન થાય છે. તે બધા અલગ-અલગ વિભાગો (Auth, Dashboard, Expenses, Categories) ને જોડે છે અને **CORS** (જેથી React ફ્રન્ટએન્ડ અને Python બેકએન્ડ એકબીજા સાથે વાત કરી શકે) ચાલુ કરે છે.

2. **`backend/config.py` (સેટિંગ્સ ફાઈલ):**
   - આ ફાઈલમાં સર્વરના પાસવર્ડ્સ, ડેટાબેઝની લિંક (`DATABASE_URL`), અને સિક્યુરિટી કી (`JWT_SECRET`) જેવી ગોઠવણી (Configuration) રાખવામાં આવે છે.

3. **`backend/controllers/` (કામ કરનાર મુખ્ય અધિકારીઓ / Controllers):**
   - કંટ્રોલર એટલે એવી ફાઈલો જ્યાં ખરેખર બિઝનેસ લોજિક (ગણતરી) લખેલું હોય છે:
     - **`auth_controller.py`:** નવું એકાઉન્ટ બનાવવું (Register), લોગ-ઈન કરવું (Login), પાસવર્ડને સિક્યોર (Hash) કરવો અને બધા રજીસ્ટર્ડ યુઝર્સનું લિસ્ટ આપવું.
     - **`dashboard_controller.py`:** ડેશબોર્ડ માટે લોગ-ઈન થયેલા યુઝરનો પોતાનો ખર્ચ (`Total Expenses`), લેવાના બાકી પૈસા (`To Receive`), આપવાના બાકી પૈસા (`To Pay`), અને ચાર્ટનો ડેટા તૈયાર કરવો.
     - **`expense_controller.py`:** ખર્ચ ઉમેરવો, ખર્ચમાં સુધારો કરવો (Edit), સ્ટેટસ `COMPLETED` થાય ત્યારે બધા સભ્યોને `Settled` કરવા, ખર્ચ ડિલીટ કરવો અને ફિલ્ટર (Search, Date, Sort) કરવા.
     - **`category_controller.py`:** કેટેગરી (જેમ કે Food, Travel, Groceries) જોવા, નવી બનાવવા, નામ બદલવા અને ડિલીટ કરવાનું કામ કરે છે.

4. **`backend/services/audit_service.py` (ડિટેક્ટિવ / હિસ્ટ્રી રેકોર્ડર):**
   - જ્યારે પણ કોઈ યુઝર ખર્ચમાં ફેરફાર કરે (દા.ત. રકમ ₹500 માંથી ₹600 કરે કે સ્ટેટસ `PENDING` માંથી `COMPLETED` કરે), ત્યારે આ ફાઈલ જૂના અને નવા ડેટાની સરખામણી કરે છે અને **Logs** માટે નોંધ તૈયાર કરે છે.

5. **`backend/prisma/schema.prisma` (ડેટાબેઝનો નકશો):**
   - જેમ મકાન બનાવતા પહેલાં આર્કિટેક્ટ નકશો બનાવે, તેમ ડેટાબેઝમાં કયા ટેબલ હશે અને કઈ કોલમ હશે તેનો આખો નકશો આ ફાઈલમાં લખેલો છે.

## 4. ડેટાબેઝનું માળખું અને ટેબલ્સ વચ્ચેનો સંબંધ (Database Schema, Tables & Relationships)

આ પ્રોજેક્ટના ડેટાબેઝમાં કુલ **5 મુખ્ય ટેબલ્સ (Models)** છે.

### ટેબલ 1: `User` (યુઝર્સનું ટેબલ)
આ ટેબલમાં એપ વાપરનાર દરેક વ્યક્તિની માહિતી સેવ થાય છે.
- `id`: દરેક યુઝરનો યુનિક નંબર (Primary Key - દા.ત. 1, 2, 3)
- `name`: યુઝરનું પૂરું નામ (દા.ત. "Rutvik", "Alice Johnson")
- `email`: યુઝરનું ઈમેઈલ એડ્રેસ (જે હંમેશા યુનિક હોય છે)
- `passwordHash`: યુઝરનો છુપાવેલો (Encrypted) પાસવર્ડ
- `isActive`: એકાઉન્ટ ચાલુ છે કે નહીં (`true` / `false`)
- `createdAt` & `updatedAt`: એકાઉન્ટ ક્યારે બન્યું અને ક્યારે અપડેટ થયું તેનો સમય

### ટેબલ 2: `Category` (ખર્ચના પ્રકારનું ટેબલ)
આ ટેબલમાં ખર્ચની કેટેગરી (જેમ કે Travel, Food & Dining, Groceries) સેવ થાય છે.
- `id`: કેટેગરીનો યુનિક નંબર (Primary Key)
- `name`: કેટેગરીનું નામ (Unique)
- `icon`: કેટેગરીના આઈકોનનું નામ (દા.ત. `utensils`, `plane`)
- `createdById`: આ કેટેગરી કયા યુઝરે બનાવી તેનો ID (Foreign Key -> `User.id`)
- `createdAt` & `updatedAt`: સમયની નોંધ

### ટેબલ 3: `Expense` (મુખ્ય ખર્ચનું ટેબલ)
આ ટેબલમાં દરેક ખર્ચની મુખ્ય વિગતો સેવ થાય છે.
- `id`: ખર્ચનો યુનિક નંબર (Primary Key)
- `title`: ખર્ચનું નામ (દા.ત. "Weekend Dinner")
- `description`: વધારાની નોંધ (Optional)
- `amount`: કુલ રકમ (Decimal - દા.ત. `2400.00`)
- `currency`: ચલણ (ડિફોલ્ટ `"INR"` / `₹`)
- `status`: ખર્ચનું સ્ટેટસ (`PENDING` અથવા `COMPLETED`)
- `expenseDate`: ખર્ચ કઈ તારીખે થયો
- `categoryId`: કઈ કેટેગરીનો ખર્ચ છે (Foreign Key -> `Category.id`)
- `createdById`: એપમાં આ ખર્ચની એન્ટ્રી કોણે પાડી (Foreign Key -> `User.id`)
- `paidById`: બિલના પૈસા ખરેખર કોણે ચૂકવ્યા (Foreign Key -> `User.id`)
- `createdAt` & `updatedAt`: સમયની નોંધ

### ટેબલ 4: `ExpenseParticipant` (ખર્ચના ભાગલા / Split ટેબલ)
જ્યારે એક ખર્ચ 4 મિત્રો વચ્ચે વહેંચાય, ત્યારે દરેક મિત્રના ભાગમાં કેટલા રૂપિયા આવ્યા અને તેણે પૈસા આપી દીધા કે બાકી છે, તે આ ટેબલમાં સેવ થાય છે.
- `id`: યુનિક નંબર (Primary Key)
- `expenseId`: કયા ખર્ચનો ભાગ છે (Foreign Key -> `Expense.id`)
- `userId`: કયા સભ્યનો ભાગ છે (Foreign Key -> `User.id`)
- `shareAmount`: આ સભ્યના ભાગમાં આવેલી રકમ (દા.ત. `₹600.00`)
- `isSettled`: શું આ સભ્યએ પૈસા ચૂકવી દીધા છે? (`true` = Settled, `false` = Pending)
- `settledAt`: ક્યારે હિસાબ પૂરો થયો તેનો સમય

### ટેબલ 5: `ExpenseAuditLog` (Logs / ફેરફારની હિસ્ટ્રીનું ટેબલ)
ખર્ચમાં થયેલા દરેક ફેરફારની નોંધ (Logs) આ ટેબલમાં રહે છે.
- `id`: લોગનો યુનિક નંબર (Primary Key)
- `expenseId`: કયા ખર્ચનો લોગ છે (Foreign Key -> `Expense.id`)
- `actorId`: ફેરફાર કોણે કર્યો (Foreign Key -> `User.id`)
- `action`: શું કામ થયું (`CREATED`, `UPDATED`, `STATUS_CHANGED`, `SETTLED`, `DELETED`)
- `summary`: ટૂંકી સમજૂતી (દા.ત. `"Status updated to COMPLETED"`)
- `diff`: જૂની અને નવી કિંમતનો તફાવત (JSON ફોર્મેટમાં)
- `createdAt`: ફેરફાર ક્યારે થયો તેનો સમય

---

### ટેબલ્સ વચ્ચેનો સંબંધ (Relationships — સરળ ઉદાહરણ સાથે):

ડેટાબેઝમાં ટેબલ્સ એકબીજા સાથે **Foreign Key (ફોરેન કી)** થી જોડાયેલા હોય છે:

1. **User અને Expense વચ્ચે `One-to-Many (1:N)` સંબંધ:**
   - **અર્થ:** એક યુઝર (`User`) અનેક ખર્ચાઓ (`Expense`) બનાવી કે ચૂકવી શકે છે.
   - **ઉદાહરણ:** Rutvik (`User.id = 1`) મહિનામાં 20 અલગ-અલગ ખર્ચા કરી શકે છે. તેથી `Expense` ટેબલમાં `paidById = 1` અને `createdById = 1` લખવામાં આવે છે.

2. **Category અને Expense વચ્ચે `One-to-Many (1:N)` સંબંધ:**
   - **અર્થ:** એક કેટેગરીમાં અનેક ખર્ચા હોઈ શકે છે, પણ એક ખર્ચની કેટેગરી એક જ હોય.
   - **ઉદાહરણ:** `"Travel"` (`Category.id = 2`) કેટેગરીની અંદર બસની ટિકિટ, પેટ્રોલ અને હોટલ એમ 10 ખર્ચા હોઈ શકે છે. જો કોઈ કેટેગરીમાં ખર્ચા હોય, તો ડેટાબેઝ તે કેટેગરીને ભૂલથી પણ ડિલીટ થવા દેતું નથી (`onDelete: Restrict`).

3. **Expense અને ExpenseParticipant વચ્ચે `One-to-Many (1:N)` સંબંધ:**
   - **અર્થ:** એક ખર્ચ (`Expense`) માં ઘણા બધા સભ્યો (`ExpenseParticipant`) ભાગીદાર હોઈ શકે છે.
   - **ઉદાહરણ:** જો `"પીઝા પાર્ટી"` (`Expense.id = 101`) માં 4 મિત્રો હોય, તો `ExpenseParticipant` ટેબલમાં `expenseId = 101` વાળી 4 લાઈન બનશે. જો મુખ્ય ખર્ચ ડિલીટ કરવામાં આવે, તો તેના ભાગલા પણ આપોઆપ ડિલીટ થઈ જાય છે (`onDelete: Cascade`).

4. **Expense અને ExpenseAuditLog વચ્ચે `One-to-Many (1:N)` સંબંધ:**
   - **અર્થ:** એક ખર્ચમાં જેટલી વાર સુધારા થાય તેટલા બધા `Logs` બની શકે છે.

## 5. બધા API નું લિસ્ટ અને સ્ટ્રક્ચર (Complete API Structure & Documentation)

નીચે પ્રોજેક્ટના તમામ **REST API Endpoints** ની સંપૂર્ણ યાદી આપેલી છે:

### A. Authentication APIs (લોગ-ઈન અને રજીસ્ટ્રેશન માટે)

#### 1. `POST /api/auth/register`
- **આ API શું કામ કરે છે?:** નવા યુઝરનું એકાઉન્ટ બનાવે છે.
- **અંદર શું મોકલવાનું? (Request Body):**
  ```json
  {
    "name": "Rutvik Sureliya",
    "email": "rutvik@example.com",
    "password": "password123"
  }
  ```
- **જવાબમાં શું મળશે? (Response - 201 Created):**
  ```json
  {
    "success": true,
    "message": "User registered successfully",
    "user": {
      "id": 5,
      "name": "Rutvik Sureliya",
      "email": "rutvik@example.com"
    }
  }
  ```

#### 2. `POST /api/auth/login`
- **આ API શું કામ કરે છે?:** યુઝરના ઈમેઈલ અને પાસવર્ડ તપાસીને તેને લોગ-ઈન કરે છે અને સિક્યુરિટી ટોકન (`JWT Token`) આપે છે.
- **અંદર શું મોકલવાનું? (Request Body):**
  ```json
  {
    "email": "rutvik@example.com",
    "password": "password123"
  }
  ```
- **જવાબમાં શું મળશે? (Response - 200 OK):**
  ```json
  {
    "success": true,
    "token": "eyJhbGciOiJIUzI1NiIsInR...",
    "user": {
      "id": 5,
      "name": "Rutvik Sureliya",
      "email": "rutvik@example.com"
    }
  }
  ```

#### 3. `GET /api/auth/users`
- **આ API શું કામ કરે છે?:** એપમાં રજીસ્ટર થયેલા બધા યુઝર્સનું લિસ્ટ આપે છે (જેથી ખર્ચ ઉમેરતી વખતે `"Paid by"` અને `"Split With"` માં બધાના નામ દેખાય).
- **અંદર શું મોકલવાનું?:** Header માં `Authorization: Bearer <token>`.
- **જવાબમાં શું મળશે? (Response - 200 OK):**
  ```json
  {
    "success": true,
    "users": [
      { "id": 1, "name": "Alice Johnson", "email": "alice@example.com" },
      { "id": 5, "name": "Rutvik Sureliya", "email": "rutvik@example.com" }
    ]
  }
  ```

### C. Expenses APIs (ખર્ચાઓના મેનેજમેન્ટ માટે)

#### 5. `GET /api/expenses`
- **આ API શું કામ કરે છે?:** બધા ખર્ચાઓનું લિસ્ટ ફિલ્ટર અને સોર્ટિંગ સાથે આપે છે.

  - `date_range`: `all` | `week` | `month` | `year` | `custom`
  - `paid_by`: યુઝરનો ID (અથવા `all`)
  - `sort`: `newer` | `older` | `amount_high` | `amount_low`
  - `search`: સર્ચ કરવાનો શબ્દ
- **જવાબમાં શું મળશે? (Response - 200 OK):**
  ```json
  {
    "success": true,
    "count": 1,
    "expenses": [
      {
        "id": 101,
        "title": "rushangi a didha",
        "amount": 500.00,
        "currency": "INR",
        "status": "PENDING",
        "categoryId": 2,
        "categoryName": "Travel",
        "paidById": 5,
        "paidByName": "rushangi",
        "participants": [
          {
            "userId": 1,
            "name": "Alice Johnson",
            "shareAmount": 100.00,
            "isSettled": false,
            "owesToName": "rushangi"
          }
        ],
        "auditTrail": [ ... ]
      }
    ]
  }
  ```

#### 6. `GET /api/expenses/<expense_id>`
- **આ API શું કામ કરે છે?:** કોઈ એક ચોક્કસ ખર્ચની સંપૂર્ણ વિગત, દરેક સભ્યના ભાગલા (`Split Distribution`) અને નીચેના `Logs` આપે છે.
- **અંદર શું મોકલવાનું?:** URL માં ખર્ચનો ID (દા.ત. `/api/expenses/101`).
- **જવાબમાં શું મળશે? (Response - 200 OK):** તે ખર્ચનો સંપૂર્ણ ઓબ્જેક્ટ અને તેનો `auditTrail` (Logs) એરે.

#### 7. `POST /api/expenses`
- **આ API શું કામ કરે છે?:** નવો ખર્ચ ડેટાબેઝમાં સેવ કરે છે અને પસંદ કરેલા સભ્યો વચ્ચે સરખા ભાગે રકમ વહેંચે છે.
- **અંદર શું મોકલવાનું? (Request Body):**
  ```json
  {
    "title": "Weekend Dinner",
    "description": "Friends dinner",
    "amount": 2000,
    "categoryId": 1,
    "paidById": 5,
    "participantUserIds": [1, 2, 3, 5],
    "expenseDate": "2026-10-23T18:00:00Z"
  }
  ```
- **જવાબમાં શું મળશે? (Response - 201 Created):** નવો બનેલો ખર્ચ અને તેના દરેક સભ્યના ભાગલા (`₹500 / person`).

#### 8. `PUT /api/expenses/<expense_id>` (અથવા `PATCH`)
- **આ API શું કામ કરે છે?:** ખર્ચની વિગત (રકમ, નામ, સભ્યો) અથવા તેનું સ્ટેટસ (`PENDING` ➔ `COMPLETED`) અપડેટ કરે છે. જ્યારે સ્ટેટસ `COMPLETED` કરવામાં આવે ત્યારે ડેટાબેઝમાં બધા સભ્યોને `isSettled: true` કરી દે છે અને નવો `Log` ઉમેરે છે.
- **અંદર શું મોકલવાનું? (Request Body):**
  ```json
  {
    "status": "COMPLETED"
  }
  ```
- **જવાબમાં શું મળશે? (Response - 200 OK):** અપડેટ થયેલો ખર્ચ (જેમાં બધા સભ્યો `isSettled: true` થઈ ગયા હશે) અને અપડેટેડ `Logs`.

#### 9. `DELETE /api/expenses/<expense_id>`
- **આ API શું કામ કરે છે?:** ખર્ચને ડેટાબેઝમાંથી કાયમી ડિલીટ કરે છે.
- **અંદર શું મોકલવાનું?:** URL માં ખર્ચનો ID.
- **જવાબમાં શું મળશે? (Response - 200 OK):**
  ```json
  {
    "success": true,
    "message": "Expense deleted successfully"
  }
  ```

## 6. પ્રોજેક્ટ ચાલુ કરવાની રીત (Setup & Run Guide)

### 1. મુખ્ય નવું ફીચર: વોલેટ અને એડવાન્સ ડિપોઝિટ સિસ્ટમ (Group/Person-wise Wallet & Deposit System)

#### A. તમારા આઈડિયાનું વિશ્લેષણ અને શ્રેષ્ઠ એકાઉન્ટિંગ પદ્ધતિ (Flow & Logic Optimization)

**તમારો મૂળ વિચાર (Raw Idea):**
દરેક સભ્ય શરૂઆતમાં અમુક રકમ (Deposit) જમા કરાવે, અને જેમ-જેમ ખર્ચા ઉમેરાતા જાય તેમ-તેમ દરેકના ભાગની રકમ તેની જમા કરેલી ડિપોઝિટમાંથી કપાતી જાય. છેલ્લે કોના કેટલા રૂપિયા વધ્યા છે અને કોણે હજુ પૈસા જમા કરાવવાના બાકી છે (Negative / Due Balance) તે દેખાય.

**આર્કિટેક્ચરલ રિવ્યુ અને શ્રેષ્ઠ પદ્ધતિ (Why "Immutable Ledger + Member Wallet Pool" is Best):**
તમારો વિચાર રુમમેટ્સ, ઓફિસ ગ્રુપ કે ટૂર/પ્રવાસ માટે **100% પ્રેક્ટિકલ** છે! પરંતુ જો આપણે ડેટાબેઝમાં ફક્ત એક સાદો નંબર (`balance = 2000`) રાખીને તેમાંથી સીધા પૈસા બાદ કરતા જઈશું, તો ભવિષ્યમાં મોટી સમસ્યા થઈ શકે છે:
- ધારો કે કોઈ ખર્ચ ₹1000 ને બદલે ભૂલથી ₹10,000 લખાઈ ગયો અને પછી યુઝર તેને **Edit** કરે કે **Delete** કરે, તો કોના ખાતામાં કેટલા પાછા ઉમેરવા તેની ગણતરીમાં ભૂલ થઈ શકે છે.

**શ્રેષ્ઠ ઉપાય — "Hybrid Shared Pool + Immutable Ledger Approach" (બેંક ખાતાવહી જેવી સિસ્ટમ):**
આપણે **બેંકની પાસબુક (Ledger)** જેવી સિસ્ટમ બનાવીશું:
1. **Individual Member Wallet (વ્યક્તિગત વોલેટ ખાતું):** દરેક યુઝરનું પોતાનું વોલેટ કાર્ડ હશે, જેમાં 3 આંકડા હંમેશા સ્પષ્ટ દેખાશે:
   - **કુલ જમા કરેલી રકમ (`Total Deposited`)**
   - **કુલ વપરાયેલો ભાગ (`Total Expense Share Used`)**
   - **હાલનું ચોખ્ખું બેલેન્સ (`Current Net Balance = Total Deposited - Total Expense Share Used`)**
2. **Payment Mode Choice (ખર્ચ ક્યાંથી થયો?):** જ્યારે ખર્ચ ઉમેરવામાં આવે ત્યારે બે વિકલ્પ મળશે:
   - **Option 1: Paid from Wallet Pool (જમા કરેલા વોલેટ/ગલ્લામાંથી):** દરેક સભ્યના ભાગની રકમ સીધી તેમના વોલેટ બેલેન્સમાંથી કપાઈ જશે અને ખર્ચ તરત જ **Settled** ગણાશે (કારણ કે પૈસા અગાઉથી જમા હતા).
   - **Option 2: Paid by Individual Pocket (કોઈ એક વ્યક્તિના પોતાના ખિસ્સામાંથી):** જો કોઈ સભ્ય પોતાના ખિસ્સામાંથી ચૂકવે, તો પણ વોલેટ બેલેન્સ સાથે તેને એડજસ્ટ કરી શકાય અથવા અત્યારની જેમ અલગ રાખી શકાય.
3. **Immutable Wallet Ledger (`WalletTransaction` ટેબલ):** જ્યારે પણ કોઈ પૈસા જમા કરાવે (`CREDIT`), ખર્ચ કપાય (`DEBIT`), કે ખર્ચ ડિલીટ થવાથી પૈસા પાછા આવે (`REFUND/REVERSAL`), ત્યારે પાસબુકની જેમ દરેક એન્ટ્રી તારીખ સાથે નોંધાશે!

#### B. ગણિતના ઉદાહરણ સાથે સંપૂર્ણ એન્ડ-ટુ-એન્ડ ફ્લો (Complete End-to-End Flow with Math Example)

ધારો કે **3 મિત્રો (Rutvik, Alice, અને Bob)** ગોવા ટ્રિપ અથવા ફ્લેટના ખર્ચ માટે વોલેટ શરૂ કરે છે:

##### સ્ટેપ 1: શરૂઆતની ડિપોઝિટ જમા કરાવવી (Initial Deposits)
- **Rutvik** વોલેટમાં **₹2,000** જમા કરાવે છે.
- **Alice** વોલેટમાં **₹2,000** જમા કરાવે છે.
- **Bob** પાસે અત્યારે ઓછા પૈસા હોવાથી તે **₹1,000** જમા કરાવે છે.

> **વોલેટની સ્થિતિ (સ્ટેપ 1 પછી):**
> - **કુલ ગ્રુપ વોલેટ પૂલ (Total Pool Balance):** `₹5,000`
> - **Rutvik નું બેલેન્સ:** `+₹2,000` (Safe / જમા)
> - **Alice નું બેલેન્સ:** `+₹2,000` (Safe / જમા)
> - **Bob નું બેલેન્સ:** `+₹1,000` (Safe / જમા)

---

##### સ્ટેપ 2: પહેલો ખર્ચ ઉમેરાય છે (Expense #1 — હોટલ ડિનર: ₹1,500)
- ત્રણેય મિત્રો જમવા જાય છે અને બિલ **₹1,500** આવે છે, જે ત્રણેય વચ્ચે સરખા ભાગે વહેંચાય છે (`₹1,500 ÷ 3 = ₹500 પ્રતિ વ્યક્તિ`).
- સિસ્ટમ આપોઆપ દરેકના વોલેટમાંથી **₹500** કાપી લેશે (`DEBIT`):

> **વોલેટની સ્થિતિ (સ્ટેપ 2 પછી):**
> - **કુલ ગ્રુપ વોલેટ પૂલ:** `₹5,000 - ₹1,500 = ₹3,500`
> - **Rutvik:** જમા `₹2,000` - વપરાયા `₹500` = **`+₹1,500` બાકી**
> - **Alice:** જમા `₹2,000` - વપરાયા `₹500` = **`+₹1,500` બાકી**
> - **Bob:** જમા `₹1,000` - વપરાયા `₹500` = **`+₹500` બાકી**

---

##### સ્ટેપ 3: બીજો ખર્ચ ઉમેરાય છે અને એક સભ્યનું બેલેન્સ માઈનસમાં જાય છે (Expense #2 — ટ્રાવેલ બુકિંગ: ₹1,800)
- હવે ત્રણેય માટે **₹1,800** નું ટ્રાવેલ બુકિંગ થાય છે (`₹1,800 ÷ 3 = ₹600 પ્રતિ વ્યક્તિ`).
- અહીં જુઓ: **Bob** ના ખાતામાં ફક્ત **₹500** જ બચ્યા હતા, પણ તેના ભાગનો ખર્ચ **₹600** આવ્યો!
- સિસ્ટમ ખર્ચ રોકશે નહીં, પણ Bob નું ખાતું **`-₹100` (Due / ખૂટતી રકમ)** બતાવશે:

> **વોલેટની સ્થિતિ (સ્ટેપ 3 પછી):**
> - **કુલ ગ્રુપ વોલેટ પૂલ:** `₹3,500 - ₹1,800 = ₹1,700`
> - **Rutvik:** જમા `₹2,000` - કુલ વપરાયા `₹1,100` = **`+₹900` (Available)**
> - **Alice:** જમા `₹2,000` - કુલ વપરાયા `₹1,100` = **`+₹900` (Available)**
> - **Bob:** જમા `₹1,000` - કુલ વપરાયા `₹1,100` = **`-₹100` (⚠️ Needs to add ₹100 / ₹100 જમા કરાવવાના બાકી)**

---

##### સ્ટેપ 4: Bob નવી ડિપોઝિટ ઉમેરે છે (Top-Up / Settlement)
- સ્ક્રીન પર Bob ના નામ સામે લાલ બેજ દેખાશે: **`"Due: ₹100 (Add Deposit)"`**.
- જ્યારે Bob બીજા **₹500** જમા કરાવશે, ત્યારે તેનું કુલ જમા `₹1,500` થશે અને તેનું બેલેન્સ `-₹100 + ₹500 = +₹400` (પાછું પોઝિટિવ/ગ્રીન) થઈ જશે!

#### C. ડેટાબેઝ અને API માં શું ફેરફાર થશે? (Database & API Impact — Planning Only)

જ્યારે આપણે આ ફીચર કોડ કરીશું, ત્યારે નીચે મુજબના નવા ટેબલ્સ અને API ઉમેરાશે:

##### 1. નવા ડેટાબેઝ ટેબલ્સ (Prisma Models):
- **ટેબલ A: `MemberWallet` (દરેક યુઝરનું વોલેટ ખાતું)**
  - `id`: Primary Key
  - `userId`: કયા યુઝરનું વોલેટ છે (Unique Foreign Key -> `User.id`)
  - `totalDeposited`: અત્યાર સુધી જમા કરાવેલી કુલ રકમ (`Decimal`)
  - `totalSpentShare`: ખર્ચાઓમાં કપાયેલી કુલ રકમ (`Decimal`)
  - `currentBalance`: હાલનું બેલેન્સ (`totalDeposited - totalSpentShare`, પોઝિટિવ કે નેગેટિવ હોઈ શકે)
  - `updatedAt`: છેલ્લા ફેરફારનો સમય

- **ટેબલ B: `WalletTransaction` (વોલેટની પાસબુક / Ledger ટેબલ)**
  - `id`: Primary Key
  - `userId`: કયા સભ્યના વોલેટમાં અસર થઈ (Foreign Key -> `User.id`)
  - `type`: ટ્રાન્ઝેક્શનનો પ્રકાર (`DEPOSIT_ADDED`, `EXPENSE_DEDUCTED`, `EXPENSE_REFUNDED`, `EXPENSE_ADJUSTED`)
  - `amount`: કેટલા રૂપિયા ઉમેરાયા કે કપાયા (`+2000` અથવા `-500`)
  - `balanceAfter`: આ એન્ટ્રી પછી ખાતામાં કેટલા રૂપિયા રહ્યા
  - `expenseId`: જો ખર્ચના કારણે પૈસા કપાયા હોય તો તે ખર્ચનો ID (Optional Foreign Key -> `Expense.id`)
  - `note`: નોંધ (દા.ત. `"October Advance Deposit"` અથવા `"Share for Weekend Dinner"`)
  - `recordedById`: એન્ટ્રી કોણે પાડી (Foreign Key -> `User.id`)
  - `createdAt`: તારીખ અને સમય

- **ટેબલ C: `Expense` ટેબલમાં 1 નવી કોલમ:**
  - `paymentMode`: `"WALLET_POOL"` (વોલેટમાંથી કપાયા) અથવા `"DIRECT_SPLIT"` (સીધા વ્યક્તિગત ચૂકવ્યા)

##### 2. નવા API Endpoints (પ્લાનિંગ):
1. **`GET /api/wallet/overview`** — આખા ગ્રુપનું કુલ જમા બેલેન્સ, કુલ વપરાયેલી રકમ, અને દરેક સભ્યનું વ્યક્તિગત બેલેન્સ (કોણ પ્લસમાં છે અને કોણ માઈનસમાં છે) આપશે.
2. **`POST /api/wallet/deposit`** — કોઈ સભ્યના નામ પર નવી ડિપોઝિટ રકમ ઉમેરવા માટે (`{ "userId": 2, "amount": 2000, "note": "Initial Deposit" }`).
3. **`GET /api/wallet/transactions`** — બેંકના સ્ટેટમેન્ટની જેમ વોલેટમાં ક્યારે કેટલા જમા થયા અને કયા ખર્ચમાં કેટલા કપાયા તેની સંપૂર્ણ હિસ્ટ્રી (Filter by User સાથે) આપશે.
4. **`PUT /api/wallet/deposit/<id>` & `DELETE /api/wallet/deposit/<id>`** — ભૂલથી ખોટી ડિપોઝિટ લખાઈ ગઈ હોય તો તેને સુધારવા કે રદ કરવા માટે.

### 2. પ્રોજેક્ટને વધુ પાવરફુલ બનાવવા માટે 6 નવા ફીચર્સ (Future Feature Suggestions)

વોલેટ સિસ્ટમ ઉપરાંત, આ પ્રોજેક્ટને એક રિયલ-વર્લ્ડ પ્રોડક્ટ બનાવવા માટે આપણે નીચેના **6 હાઈ-ઈમ્પેક્ટ ફીચર્સ** ઉમેરી શકીએ છીએ:

1. **Unequal / Custom Split Modes (અલગ-અલગ રકમથી ભાગ પાડવાની સુવિધા):**
   - **કેમ ઉપયોગી છે?:** અત્યારે બિલ બધા સભ્યો વચ્ચે સરખા ભાગે (`Equal Split`) વહેંચાય છે. પણ ઘણીવાર કોઈ મિત્રએ ₹300 ની વસ્તુ લીધી હોય અને બીજાએ ₹700 ની લીધી હોય. ત્યારે **Exact Amount Split (₹)** અથવા **Percentage Split (%)** નો વિકલ્પ ખૂબ કામ લાગે છે.
2. **Partial Settlement & Settlement History (ટુકડે-ટુકડે પૈસા ચૂકવવાની સુવિધા):**
   - **કેમ ઉપયોગી છે?:** જો કોઈ સભ્યએ ₹1,000 આપવાના હોય અને તે અત્યારે ₹400 આપે, તો તેને રેકોર્ડ કરવાની સુવિધા જેથી બાકીના ₹600 જ Pending બતાવે.
3. **Monthly Budget Limit & Smart Progress Bar (માસિક બજેટ અને વોર્નિંગ એલર્ટ):**
   - **કેમ ઉપયોગી છે?:** યુઝર પોતાનું કે દરેક કેટેગરીનું માસિક બજેટ (દા.ત. Food માટે ₹5,000) સેટ કરી શકે. જ્યારે 80% ખર્ચ પહોંચે ત્યારે પીળા રંગની અને 100% વટાવે ત્યારે લાલ રંગની એલર્ટ બતાવે.
4. **One-Click PDF & Excel (CSV) Report Export (હિસાબનો રિપોર્ટ ડાઉનલોડ કરવો):**
   - **કેમ ઉપયોગી છે?:** મહિનાના અંતે આખા ગ્રુપનો હિસાબ, વોલેટ સ્ટેટમેન્ટ અને દરેકના બાકી પૈસાનું લિસ્ટ **PDF** કે **Excel** માં ડાઉનલોડ કરીને સીધું WhatsApp ગ્રુપમાં શેર કરી શકાય.
5. **Recurring Expenses / Auto-Bills (દર મહિને આવતા ફિક્સ ખર્ચા):**
   - **કેમ ઉપયોગી છે?:** ઘરનું ભાડું, Wi-Fi બિલ, કે દૂધનું બિલ દર મહિને ફિક્સ હોય છે. તેને એકવાર સેટ કરવાથી દર મહિનાની 1 તારીખે આપોઆપ ડ્રાફ્ટ કે ખર્ચ તરીકે ઉમેરાઈ જાય.
6. **Digital Bill / Receipt Note & Tagging (બિલના ફોટા અને ટેગ્સ):**
   - **કેમ ઉપયોગી છે?:** મોટા ખર્ચાઓ (જેમ કે ઈલેક્ટ્રોનિક્સ કે ટ્રિપના બિલ) સાથે બિલનો ફોટો કે `#GoaTrip2026` જેવા ટેગ્સ જોડવાથી જૂના બિલ શોધવા સહેલા પડે છે.

### 3. સ્ટેપ-બાય-સ્ટેપ અમલીકરણ રોડમેપ (Task-wise Step-by-Step Execution Process)

જ્યારે આપણે આ વોલેટ સિસ્ટમ બનાવવાનું શરૂ કરીશું, ત્યારે કોઈ પણ બગ (Bug) વગર કામ પૂરું કરવા માટે નીચેના **4 તબક્કા (Phases)** માં કોડિંગ કરીશું:

---

#### Phase 1: Database Schema Updates (ડેટાબેઝમાં ફેરફાર)
- [ ] **Task 1.1:** `backend/prisma/schema.prisma` અને `src/types/index.ts` માં `MemberWallet` અને `WalletTransaction` ના મોડેલ/ઈન્ટરફેસ ઉમેરવા.
- [ ] **Task 1.2:** `Expense` મોડેલમાં `deductFromWallet: boolean` (શું આ ખર્ચ વોલેટ ડિપોઝિટમાંથી કાપવો છે?) નામનું ફિલ્ડ ઉમેરવું.
- [ ] **Task 1.3:** `AuditAction` enum માં `WALLET_DEPOSIT` અને `WALLET_DEDUCTION` ના પ્રકાર ઉમેરવા.

---

#### Phase 2: Backend API & Calculation Logic (બેકએન્ડ અને ગણતરીનું લોજિક)
- [ ] **Task 2.1 (`Deposit Logic`):** નવી ડિપોઝિટ ઉમેરવાનું ફંક્શન બનાવવું, જે સભ્યના `totalDeposited` માં રકમ ઉમેરે અને `WalletTransaction` માં `+₹Amount` ની એન્ટ્રી પાડે.
- [ ] **Task 2.2 (`Expense Deduction Logic`):** જ્યારે નવો ખર્ચ ઉમેરાય અને `deductFromWallet = true` હોય, ત્યારે પસંદ કરેલા દરેક સભ્યના વોલેટમાંથી તેના ભાગની રકમ (`shareAmount`) આપોઆપ બાદ કરવી અને `WalletTransaction` માં `-₹Share` ની એન્ટ્રી પાડવી.
- [ ] **Task 2.3 (`Negative / Due Detection`):** જો કોઈ સભ્યનું `currentBalance < 0` થાય, તો તેને `"DUE"` (પૈસા ખૂટે છે) સ્ટેટસ આપવું અને કેટલા રૂપિયા જમા કરાવવાના બાકી છે (`Math.abs(currentBalance)`) તેની ગણતરી કરવી.
- [ ] **Task 2.4 (`Reversal & Adjustment Logic`):** જો કોઈ ખર્ચ પાછળથી **Edit** કે **Delete** થાય, તો જૂની કપાયેલી રકમ વોલેટમાં પાછી ઉમેરવી (`REFUND`) અને નવી રકમ પ્રમાણે ફરીથી સાચો ભાગ કાપવો.

---

#### Phase 3: Frontend UI/UX Changes (સ્ક્રીન અને ડિઝાઇનના ફેરફાર)
- [ ] **Task 3.1 (`Sidebar Navigation`):** ડાબી બાજુના મેનુ (Sidebar) માં `Dashboard`, `Expenses`, `Categories` ની સાથે નવો **`Wallet & Deposits`** ટેબ ઉમેરવો.
- [ ] **Task 3.2 (`Wallet Overview Page`):**
  - સૌથી ઉપર **3 Summary Cards** બતાવવા: `Total Pool Deposited (કુલ જમા)`, `Total Pool Used (કુલ વપરાયેલ)`, અને `Remaining Pool Balance (હાલનું ગ્રુપ બેલેન્સ)`.
  - નીચે **Member-wise Wallet Cards** બતાવવા: દરેક સભ્યનું નામ, તેણે જમા કરેલા રૂપિયા, વપરાયેલા રૂપિયા, અને બાકી રહેલું બેલેન્સ (જો પ્લસમાં હોય તો લીલા રંગમાં `Available: ₹900` અને માઈનસમાં હોય તો લાલ રંગમાં `Due: -₹100 • Needs Top-up`).
- [ ] **Task 3.3 (`Add Deposit Modal`):** કોઈ પણ સભ્ય પસંદ કરીને તેના ખાતામાં નવી ડિપોઝિટ રકમ (₹) અને નોંધ ઉમેરવાનું સરળ ફોર્મ બનાવવું.
- [ ] **Task 3.4 (`Wallet Passbook / Ledger Table`):** નીચે તારીખ પ્રમાણે વોલેટની પાસબુક બતાવવી, જેમાં ક્યારે કોણે પૈસા જમા કરાવ્યા (`+₹`) અને કયા ખર્ચમાં કેટલા કપાયા (`-₹`) તે સ્પષ્ટ દેખાય.
- [ ] **Task 3.5 (`Dashboard Integration`):** મુખ્ય ડેશબોર્ડ પર પણ લોગ-ઈન થયેલા યુઝરનું પોતાનું `My Wallet Balance` કાર્ડ બતાવવું.

---

#### Phase 4: Testing & Edge Cases (ખાસ પરિસ્થિતિઓનું ટેસ્ટિંગ)
- [ ] **Edge Case 1 (ખર્ચ ડિલીટ થાય ત્યારે):** જો ₹1,500 નો ખર્ચ ડિલીટ કરવામાં આવે, તો ત્રણેય સભ્યોના વોલેટમાં તેમના ₹500-₹500 આપોઆપ પાછા જમા (`Refund`) થઈ જવા જોઈએ.
- [ ] **Edge Case 2 (ખર્ચની રકમ કે સભ્યો બદલાય ત્યારે):** જો ₹1,500 નો ખર્ચ એડિટ કરીને ₹2,000 કરવામાં આવે અથવા 3 ને બદલે 4 સભ્યો કરવામાં આવે, તો જૂના ₹500 પાછા ઉમેરાઈને નવા ₹500 દરેકના ખાતામાંથી કપાવા જોઈએ.
- [ ] **Edge Case 3 (બેલેન્સ ઝીરો કે માઈનસ થાય ત્યારે):** જો કોઈ સભ્યએ ₹0 ડિપોઝિટ મૂકી હોય અને તેના ભાગમાં ₹300 નો ખર્ચ આવે, તો સિસ્ટમ ક્રેશ થયા વગર તેનું બેલેન્સ `-₹300 (Due)` બતાવવું જોઈએ.
- [ ] **Edge Case 4 (મોબાઈલ અને ડાર્ક મોડ ટેસ્ટિંગ):** નવા વોલેટ કાર્ડ્સ અને પાસબુક ટેબલ મોબાઈલ સ્ક્રીન પર અને ડાર્ક મોડમાં બિલકુલ ક્લીન દેખાવા જોઈએ.
